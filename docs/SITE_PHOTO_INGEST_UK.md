# Безпечне додавання фото обкладинки із сайту

Цей канал призначений для фотографії, яку бібліотекар завантажив і підтвердив
у захищеному кабінеті сайту. Він не замінює пошук обкладинки за URL.

## 1. Контракт одного запиту

Сервер сайту створює в гілці `main` рівно один текстовий файл:

```text
imports/site/<CAT-ID>--<UUID>--ow0.jpg.b64
```

Приклад:

```text
imports/site/CAT-0112--11111111-1111-4111-8111-111111111111--ow0.jpg.b64
```

Правила:

- `CAT-ID` має формат `CAT-` і щонайменше чотири цифри;
- `UUID` генерує сервер сайту; це незмінний `request_id`;
- `ow0` — безпечний стандартний режим, який не перезаписує наявний файл;
- `ow1` — явний дозвіл замінити наявну обкладинку;
- вміст файла — лише base64 фотографії, без префікса
  `data:image/...;base64,` і без JSON;
- один файл містить одне зображення.

Не формуйте шлях із довільного імені файла користувача. Сервер має сам
побудувати його з перевіреного CAT-ID, нового UUID та дозволеного `ow0/ow1`.

## 2. Що робить GitHub Actions

Push файла в `imports/site/*.jpg.b64` запускає
`.github/workflows/import-site-photo.yml`. Workflow:

1. працює лише в `main`;
2. перевіряє кожен файл окремим Python-обробником;
3. не приймає підкаталоги, `..`, symlink або інший формат назви;
4. обмежує base64-файл 14 МБ, а декодоване фото — 10 МБ;
5. декодує base64 у строгому режимі;
6. перевіряє реальний вміст через Pillow;
7. блокує decompression bomb і зображення понад 40 мільйонів пікселів;
8. враховує EXIF-орієнтацію, перетворює прозорість на білий фон та RGB;
9. зменшує зі збереженням пропорцій до максимуму 600 × 900;
10. створює JPEG із `quality=82`, `optimize=True`, `progressive=True`;
11. записує результат до `cover-status/requests/<UUID>.json`;
12. лише після запису status видаляє початковий `.b64`;
13. одним службовим commit зберігає cover, status і видалення import-файла.

Старі workflow не змінюються. Вкладений шлях `imports/site/` не збігається зі
старим шаблоном `imports/*.jpg.b64`.

## 3. Перезапис

### Стандартний запит `ow0`

- якщо `covers/<CAT-ID>.jpg` відсутній — файл створюється;
- якщо вже є і має інший вміст — повертається `already_exists`, старий файл не
  змінюється;
- якщо вже є точно такий самий оптимізований JPEG — повертається
  `already_applied`. Це безпечне відновлення після перерваного workflow.

### Підтверджена заміна `ow1`

`ow1` дозволено формувати лише після окремого попередження бібліотекарю, що
наявна обкладинка буде замінена. Заміна залишається окремим Git commit, тому її
можна перевірити в історії репозиторію.

## 4. Status JSON

Успіх:

```json
{
  "cat_id": "CAT-0112",
  "request_id": "11111111-1111-4111-8111-111111111111",
  "success": true,
  "status": "completed",
  "message": "Фотографію обкладинки додано",
  "source": "site_photo",
  "final_url": "https://raw.githubusercontent.com/nazarijshvetz1/library-covers/main/covers/CAT-0112.jpg"
}
```

Очікувана помилка:

```json
{
  "cat_id": "CAT-0112",
  "request_id": "11111111-1111-4111-8111-111111111111",
  "success": false,
  "status": "already_exists",
  "message": "Обкладинка вже існує; для свідомої заміни використайте ow1",
  "source": "site_photo"
}
```

Можливі статуси:

- `completed` — cover створено або замінено;
- `already_applied` — потрібний оптимізований файл уже був записаний;
- `already_exists` — інший cover захищено від перезапису;
- `invalid_base64` — вміст не є чистим base64;
- `unsupported_format` — декодований файл не відкривається як зображення;
- `file_too_large` — перевищено розмір або допустиму кількість пікселів.

Некоректний шлях чи назва не можуть безпечно визначити CAT-ID/request_id. Такі
файли не споживаються, status за неперевіреним іменем не створюється, а job
завершується помилкою для ручного розгляду.

## 5. Підключення сайту

GitHub API має викликати тільки серверна частина сайту:

1. перевірити авторизацію бібліотекаря;
2. отримати CAT-ID із серверної чернетки, а не з довільного browser path;
3. перевірити тип і розмір завантаженого файла до відправлення;
4. створити новий UUID;
5. за замовчуванням сформувати шлях з `ow0`;
6. створити файл через GitHub Contents API в `main`;
7. не повторювати запит з іншим UUID після timeout — спершу перевірити status
   старого UUID;
8. опитувати `cover-status/requests/<UUID>.json`;
9. записувати постійний `final_url` у Google Sheets лише після
   `success=true` і перевірки збігу CAT-ID/request_id.

Token або GitHub App credential:

- зберігається тільки в server-side secret;
- має доступ лише до цього репозиторію;
- не потрапляє до JavaScript браузера, Google Sheets, import-файла, status чи
  журналів;
- має бути відкликаний і замінений при підозрі на розкриття.

### Подвійне base64 у GitHub Contents API

Поле `content` у GitHub Contents API також приймає base64. Оскільки сам файл
`.jpg.b64` повинен містити текст base64 фотографії, сервер виконує два рівні:

1. `fileBody = base64(imageBytes)` — майбутній текст файла в репозиторії;
2. `apiContent = base64(UTF8(fileBody))` — значення поля `content` у PUT-запиті.

Якщо передати лише перший рівень як API `content`, GitHub декодує його і
збереже сирі байти зображення у `.b64`; workflow правильно відхилить такий файл
зі статусом `invalid_base64`.

## 6. Локальна перевірка

```bash
python -m pip install -r scripts/requirements.txt
python -m pytest -q tests/test_import_site_photo.py
python scripts/import_site_photo.py \
  --repo-root . \
  --input imports/site/CAT-0112--11111111-1111-4111-8111-111111111111--ow0.jpg.b64
```

Тестовий import виконуйте лише в тимчасовій копії репозиторію: успішний запуск
створює cover, status і видаляє вхідний файл.
